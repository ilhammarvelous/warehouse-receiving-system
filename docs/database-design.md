# Database Design: Warehouse Receiving System

| | |
|---|---|
| **Database** | PostgreSQL 16 |
| **Derived from** | `prd.md` (FR-*, NFR-1 to NFR-4, BR-01 to BR-24) |
| **Diagram** | `erd.mmd` |
| **Used by** | `technical-spec.md` (Sections: Database design, API flow), Laravel migrations |

> This document defines the schema that the Laravel migrations must produce. The SQL below is the reference. Laravel's schema builder does not support `CHECK` constraints, partial or expression indexes, or triggers, so these are added in migrations with `DB::statement()`. The generated schema must match this document.

---

## 1. Design Principles

1. **The database is the last line of defense.** Business rules are enforced in the service layer, and the most critical ones are repeated as database constraints (NFR-4). A bug in the application must not be able to produce negative stock or over-received items.
2. **Stock has two views that must always agree.** `inventory.quantity_on_hand` is the fast read model. `inventory_transactions` is the append-only ledger. Both are written in the same database transaction (NFR-1, NFR-2, BR-17).
3. **Concurrency is handled with row locks**, always acquired in the same order to avoid deadlocks (Section 6).
4. **History is immutable.** `receipts` and `inventory_transactions` are append-only and protected by triggers (BR-16).
5. **Small and explicit.** No tables or columns for out-of-scope features.

## 2. Conventions

| Topic | Convention |
|---|---|
| Table and column names | `snake_case`, tables in plural |
| Primary keys | `BIGINT GENERATED BY DEFAULT AS IDENTITY` (Laravel `id()` produces an equivalent `bigserial`) |
| Timestamps | `TIMESTAMPTZ`, stored in UTC (NFR-16). Use `timestampsTz()` in migrations. |
| Quantities per item | `INTEGER`, bounded by `CHECK` (maximum 1,000,000 per item) |
| Stock and balances | `BIGINT`, because the sum over time can exceed 2,147,483,647 |
| Enumerations | `VARCHAR` with a `CHECK` constraint, not native `ENUM`, because it is easier to change in migrations |
| Foreign keys | `ON DELETE RESTRICT` (the default). Nothing in this system is deleted except draft items. |
| Constraint names | Explicit, `<table>_<what>_<type>`, so error handling can map them to API error codes |

## 3. Tables Overview

| Table | Purpose | Main requirements |
|---|---|---|
| `users` | Accounts with a role | FR-AUTH-*, A-02, A-03 |
| `personal_access_tokens` | Sanctum API tokens (framework table) | FR-AUTH-1, FR-AUTH-2 |
| `products` | Products with unique SKU | FR-PROD-*, BR-01 |
| `inventory` | Current stock per product (read model) | FR-INV-1, BR-03, BR-17 |
| `document_number_sequences` | Daily counter for document numbers | FR-DOC-2, BR-19 |
| `receiving_documents` | Header of an inbound delivery with status | FR-DOC-*, FR-LIFE-* |
| `receiving_items` | Product lines with expected and received quantity | FR-DOC-4, FR-DOC-5, BR-02, BR-07 |
| `receipts` | Each recording of a received quantity (append-only) | FR-RCV-*, BR-21 |
| `inventory_transactions` | Immutable stock ledger (append-only) | FR-INV-2 to FR-INV-5, BR-13, BR-16 |
| `idempotency_keys` | Stored results of receipt requests | FR-RCV-6, BR-15, A-17 |

Relationships (details in `erd.mmd`):

- A document has one or more items. An item belongs to one document and one product.
- An item has zero or more receipts.
- Each receipt produces exactly one inventory transaction.
- A product has exactly one inventory row and many transactions.

## 4. Schema (SQL DDL)

```sql
-- =========================================================
-- users
-- =========================================================
CREATE TABLE users (
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name        VARCHAR(255) NOT NULL,
    email       VARCHAR(255) NOT NULL,
    password    VARCHAR(255) NOT NULL,                 -- bcrypt/argon2 hash
    role        VARCHAR(20)  NOT NULL,
    created_at  TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ  NOT NULL DEFAULT now(),
    CONSTRAINT users_role_check CHECK (role IN ('OPERATOR', 'SUPERVISOR'))
);
CREATE UNIQUE INDEX users_email_unique ON users (lower(email));

-- =========================================================
-- personal_access_tokens  (created by Laravel Sanctum's own migration,
-- shown here for completeness; do not hand-write it)
-- =========================================================
-- id, tokenable_type, tokenable_id, name, token (unique, hashed),
-- abilities, last_used_at, expires_at, created_at, updated_at

-- =========================================================
-- products
-- =========================================================
CREATE TABLE products (
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    sku         VARCHAR(50)  NOT NULL,
    name        VARCHAR(255) NOT NULL,
    created_by  BIGINT       NOT NULL REFERENCES users (id),
    created_at  TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ  NOT NULL DEFAULT now(),
    -- uppercase letters, digits, hyphen; must not start or end with a hyphen (BR-01)
    CONSTRAINT products_sku_format_check
        CHECK (sku ~ '^[A-Z0-9]([A-Z0-9-]*[A-Z0-9])?$'),
    CONSTRAINT products_name_not_blank_check
        CHECK (char_length(btrim(name)) >= 1)
);
CREATE UNIQUE INDEX products_sku_unique ON products (sku);

-- =========================================================
-- inventory: exactly one row per product (FR-PROD-5)
-- =========================================================
CREATE TABLE inventory (
    product_id        BIGINT      PRIMARY KEY REFERENCES products (id),
    quantity_on_hand  BIGINT      NOT NULL DEFAULT 0,
    updated_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT inventory_quantity_non_negative_check CHECK (quantity_on_hand >= 0)
);

-- =========================================================
-- document_number_sequences: atomic daily counter (A-10, BR-19)
-- =========================================================
CREATE TABLE document_number_sequences (
    sequence_date  DATE    PRIMARY KEY,
    last_number    INTEGER NOT NULL,
    CONSTRAINT document_number_sequences_positive_check CHECK (last_number >= 1)
);

-- =========================================================
-- receiving_documents
-- =========================================================
CREATE TABLE receiving_documents (
    id                 BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    document_number    VARCHAR(30)   NOT NULL,
    supplier_name      VARCHAR(255)  NOT NULL,
    expected_date      DATE          NOT NULL,
    notes              VARCHAR(1000),
    status             VARCHAR(30)   NOT NULL DEFAULT 'DRAFT',
    created_by         BIGINT        NOT NULL REFERENCES users (id),
    status_changed_by  BIGINT        REFERENCES users (id),
    status_changed_at  TIMESTAMPTZ,
    created_at         TIMESTAMPTZ   NOT NULL DEFAULT now(),
    updated_at         TIMESTAMPTZ   NOT NULL DEFAULT now(),
    CONSTRAINT receiving_documents_status_check
        CHECK (status IN ('DRAFT', 'OPEN', 'PARTIALLY_RECEIVED', 'COMPLETED', 'CANCELLED')),
    CONSTRAINT receiving_documents_number_format_check
        CHECK (document_number ~ '^RCV-[0-9]{8}-[0-9]{4,}$'),
    CONSTRAINT receiving_documents_supplier_not_blank_check
        CHECK (char_length(btrim(supplier_name)) >= 1),
    CONSTRAINT receiving_documents_status_actor_pair_check
        CHECK ((status_changed_by IS NULL) = (status_changed_at IS NULL))
);
CREATE UNIQUE INDEX receiving_documents_number_unique ON receiving_documents (document_number);
CREATE INDEX receiving_documents_status_created_idx   ON receiving_documents (status, id DESC);
CREATE INDEX receiving_documents_created_idx          ON receiving_documents (id DESC);

-- =========================================================
-- receiving_items
-- =========================================================
CREATE TABLE receiving_items (
    id                     BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    receiving_document_id  BIGINT      NOT NULL REFERENCES receiving_documents (id),
    product_id             BIGINT      NOT NULL REFERENCES products (id),
    expected_quantity      INTEGER     NOT NULL,
    received_quantity      INTEGER     NOT NULL DEFAULT 0,
    created_at             TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at             TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT receiving_items_document_product_unique
        UNIQUE (receiving_document_id, product_id),                       -- BR-02
    CONSTRAINT receiving_items_expected_range_check
        CHECK (expected_quantity BETWEEN 1 AND 1000000),                  -- BR-03
    CONSTRAINT receiving_items_received_non_negative_check
        CHECK (received_quantity >= 0),
    CONSTRAINT receiving_items_not_over_received_check
        CHECK (received_quantity <= expected_quantity)                    -- BR-07 (last line of defense)
);
CREATE INDEX receiving_items_product_idx ON receiving_items (product_id);

-- =========================================================
-- receipts: append-only (BR-16, BR-21)
-- =========================================================
CREATE TABLE receipts (
    id                 BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    receiving_item_id  BIGINT      NOT NULL REFERENCES receiving_items (id),
    quantity           INTEGER     NOT NULL,
    received_by        BIGINT      NOT NULL REFERENCES users (id),
    created_at         TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT receipts_quantity_positive_check CHECK (quantity > 0)
);
CREATE INDEX receipts_item_idx ON receipts (receiving_item_id, id);

-- =========================================================
-- inventory_transactions: append-only stock ledger (BR-13, BR-16, BR-17)
-- receiving_item_id, receiving_document_id and product_id are intentionally
-- denormalized so the history can be filtered without joins (FR-INV-4).
-- They are written in the same transaction as the receipt.
-- =========================================================
CREATE TABLE inventory_transactions (
    id                     BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    product_id             BIGINT      NOT NULL REFERENCES products (id),
    type                   VARCHAR(20) NOT NULL,
    quantity               INTEGER     NOT NULL,
    balance_after          BIGINT      NOT NULL,
    receipt_id             BIGINT      NOT NULL REFERENCES receipts (id),
    receiving_item_id      BIGINT      NOT NULL REFERENCES receiving_items (id),
    receiving_document_id  BIGINT      NOT NULL REFERENCES receiving_documents (id),
    created_by             BIGINT      NOT NULL REFERENCES users (id),
    created_at             TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT inventory_transactions_type_check     CHECK (type IN ('RECEIVE')),
    CONSTRAINT inventory_transactions_quantity_check CHECK (quantity > 0),
    CONSTRAINT inventory_transactions_balance_check  CHECK (balance_after >= quantity)
);
CREATE UNIQUE INDEX inventory_transactions_receipt_unique ON inventory_transactions (receipt_id);  -- one receipt, one transaction
CREATE INDEX inventory_transactions_product_idx  ON inventory_transactions (product_id, id DESC);
CREATE INDEX inventory_transactions_document_idx ON inventory_transactions (receiving_document_id, id DESC);

-- =========================================================
-- idempotency_keys (FR-RCV-6, BR-15, A-17)
-- Only successful results are stored. A rejected request stores nothing.
-- =========================================================
CREATE TABLE idempotency_keys (
    id               BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id          BIGINT       NOT NULL REFERENCES users (id),
    endpoint         VARCHAR(100) NOT NULL,
    idempotency_key  VARCHAR(128) NOT NULL,
    request_hash     CHAR(64)     NOT NULL,
    receipt_id       BIGINT       REFERENCES receipts (id),
    response_status  SMALLINT     NOT NULL,
    response_body    JSONB        NOT NULL,
    created_at       TIMESTAMPTZ  NOT NULL DEFAULT now(),
    CONSTRAINT idempotency_keys_scope_unique
        UNIQUE (user_id, endpoint, idempotency_key),
    CONSTRAINT idempotency_keys_key_length_check
        CHECK (char_length(idempotency_key) BETWEEN 8 AND 128)
);

-- =========================================================
-- Immutability guard for the ledger tables (BR-16)
-- =========================================================
CREATE FUNCTION prevent_row_mutation() RETURNS trigger AS $$
BEGIN
    RAISE EXCEPTION '% on % is not allowed: table is append-only', TG_OP, TG_TABLE_NAME
        USING ERRCODE = 'integrity_constraint_violation';
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER receipts_append_only
    BEFORE UPDATE OR DELETE ON receipts
    FOR EACH ROW EXECUTE FUNCTION prevent_row_mutation();

CREATE TRIGGER inventory_transactions_append_only
    BEFORE UPDATE OR DELETE ON inventory_transactions
    FOR EACH ROW EXECUTE FUNCTION prevent_row_mutation();
```

## 5. Index Rationale

| Index | Query it serves |
|---|---|
| `products_sku_unique` | Duplicate SKU check (BR-01), SKU search |
| `users_email_unique` on `lower(email)` | Login lookup, duplicate prevention |
| `receiving_documents_number_unique` | Unique document number (BR-19), search by number |
| `receiving_documents_status_created_idx` | Document list filtered by status, newest first (FR-DOC-8) |
| `receiving_documents_created_idx` | Unfiltered document list, newest first |
| `receiving_items_document_product_unique` | Prevents duplicate products in a document (BR-02), loads items of a document |
| `receiving_items_product_idx` | Foreign key lookups by product |
| `receipts_item_idx` | Receipt history of an item and of a document |
| `inventory_transactions_receipt_unique` | One transaction per receipt (BR-13) |
| `inventory_transactions_product_idx` | History filtered by product, newest first (FR-INV-4) |
| `inventory_transactions_document_idx` | History filtered by document, newest first (FR-INV-4) |
| `idempotency_keys_scope_unique` | Idempotency lookup and race protection (BR-15) |

Notes:

- "Newest first" uses `ORDER BY id DESC`. Because the transaction row is inserted while the inventory row is locked, ids increase in the same order as stock balances for one product.
- Search by SKU or name uses `ILIKE '%term%'`. At the expected volume (10,000 products, NFR-8) a sequential scan is fast enough. If it ever becomes slow, add a `pg_trgm` index. This is not needed now.

## 6. Concurrency and Locking Design

### 6.1 Lock order

Every operation that writes locks rows **in this order**, and never in reverse:

1. `receiving_documents` row (`SELECT ... FOR UPDATE`)
2. `receiving_items` row(s) (`SELECT ... FOR UPDATE`)
3. `inventory` row (`UPDATE` takes the lock implicitly)

A fixed order prevents deadlocks.

### 6.2 Why the document row is locked

Locking the document first serializes all state-changing operations on the same document: receipt, confirm, complete, cancel, and draft edits. This closes the race "operator records a receipt while a supervisor cancels or completes the same document", which item-level locking alone would not catch. Two receipts on different documents for the same product still run in parallel and only wait on the single `inventory` row.

### 6.3 Receive operation (single transaction)

This is the reference sequence for `POST` receipt. The technical specification's API flow must follow it.

```text
BEGIN
 1. SELECT * FROM receiving_documents WHERE id = :doc FOR UPDATE.
      not found                  -> 404
 2. Look up (user_id, endpoint, idempotency_key) in idempotency_keys.
      found, same request_hash   -> COMMIT, return the stored response (status, body)   [BR-15]
      found, different hash      -> ROLLBACK, 409 IDEMPOTENCY_KEY_REUSED
 3. Document status NOT IN (OPEN, PARTIALLY_RECEIVED)
                                 -> 409 DOCUMENT_NOT_RECEIVABLE                         [BR-06]
 4. SELECT * FROM receiving_items WHERE id = :item AND receiving_document_id = :doc FOR UPDATE.
      not found                  -> 404
 5. remaining = expected_quantity - received_quantity
      quantity > remaining       -> 422 QUANTITY_EXCEEDS_REMAINING                      [BR-07]
 6. UPDATE receiving_items SET received_quantity = received_quantity + :q.
 7. INSERT INTO receipts (...) RETURNING id.
 8. UPDATE inventory SET quantity_on_hand = quantity_on_hand + :q
      WHERE product_id = :p RETURNING quantity_on_hand.                                 [BR-13]
 9. INSERT INTO inventory_transactions (..., quantity = :q, balance_after = <step 8>).
10. If document status = OPEN: UPDATE receiving_documents SET status = 'PARTIALLY_RECEIVED',
      status_changed_by = :user, status_changed_at = now().                             [BR-10]
11. INSERT INTO idempotency_keys (..., response_status, response_body).
COMMIT
```

Any error rolls everything back, so a rejected operation changes nothing (BR-14).

**Why the idempotency lookup comes after the document lock but before the status check.**

- Two requests with the same key for the same document are serialized by step 1. The second one waits, then finds the stored key in step 2 and replays the stored response. Stock changes once.
- A retry that arrives after the document became `COMPLETED` still gets the original success response, because the lookup happens before the status check in step 3.
- If the same key is used at the same moment for two different documents, the locks do not serialize them. The first to commit inserts the key in step 11, and the second fails on `idempotency_keys_scope_unique`. The service must catch that unique violation, roll back, and return `409 IDEMPOTENCY_KEY_REUSED`.

### 6.4 Document number generation

Executed inside the document-creation transaction:

```sql
INSERT INTO document_number_sequences (sequence_date, last_number)
VALUES (:today_utc, 1)
ON CONFLICT (sequence_date)
DO UPDATE SET last_number = document_number_sequences.last_number + 1
RETURNING last_number;
```

The service formats the result as `RCV-` + `YYYYMMDD` + the number padded to at least 4 digits. The upsert is atomic and holds a row lock until commit, so concurrent creations never receive the same number. If the creation transaction rolls back, the counter increment also rolls back, so there are no gaps caused by failures.

### 6.5 Complete and cancel

Both lock the document row first (6.1). Complete then checks:

```sql
SELECT 1 FROM receiving_items
WHERE receiving_document_id = :doc AND received_quantity < expected_quantity
LIMIT 1;   -- any row found -> 409 DOCUMENT_NOT_FULLY_RECEIVED  [BR-08]
```

Cancel needs no item check: only `DRAFT` and `OPEN` can be cancelled, and those states cannot have receipts (BR-11).

## 7. Requirement to Constraint Mapping

| Rule | Application check | Database protection |
|---|---|---|
| BR-01 SKU unique and uppercase | Normalize and validate | `products_sku_unique`, `products_sku_format_check` |
| BR-02 One product per document | Validate request | `receiving_items_document_product_unique` |
| BR-03 Quantities are positive integers | Validate request | Integer types, `receiving_items_expected_range_check`, `receipts_quantity_positive_check`, `inventory_quantity_non_negative_check` |
| BR-07 No over-receiving | Service check under lock | `receiving_items_not_over_received_check` |
| BR-12 Status values | Service state machine | `receiving_documents_status_check` |
| BR-13 One transaction per receipt | Service | `inventory_transactions_receipt_unique` |
| BR-15 Idempotency | Service lookup | `idempotency_keys_scope_unique` |
| BR-16 Immutable history | No update or delete endpoints | Append-only triggers |
| BR-17 Stock equals ledger sum | Same-transaction writes | Verified by test and reconciliation query (Section 9) |
| BR-19 Unique document number | Sequence upsert | `receiving_documents_number_unique` |
| BR-23 No product deletion | No endpoint | Foreign keys with `RESTRICT` |
| NFR-3 Concurrency safety | Lock order (Section 6) | Row locks, check constraints |

Rules not enforced in the database (they need cross-row or workflow knowledge): status transition validity, role permissions, at least one item before confirming, "all items fully received" before completing, and "no receipts before cancel". These live in the service layer and are covered by tests.

## 8. Migration Strategy

### 8.1 Rules

1. **One migration per table**, in dependency order, so each file is small and reviewable.
2. **Never edit a migration that has been merged and run.** Fix forward with a new migration.
3. **Every migration has a working `down()`**, so rollback can be tested.
4. **`CHECK` constraints, expression indexes, and triggers** use `DB::statement()` with the exact SQL from Section 4, inside the same migration as the table.
5. **Constraint names are explicit** (Section 4), because the application maps constraint violations to API error codes (for example `products_sku_unique` to `SKU_ALREADY_EXISTS`).
6. **Migrations only change structure.** Reference or demo data goes in seeders.
7. **Timestamps use `timestampsTz()`** and the database timezone is set to UTC.

### 8.2 Migration order

| # | File (suggested) | Creates |
|---|---|---|
| 1 | `create_users_table` | `users` (with `role`, case-insensitive email index). Remove the unused Laravel defaults (`password_reset_tokens`, `sessions`), because the API uses tokens only. |
| 2 | `create_personal_access_tokens_table` | Sanctum table (published by Sanctum) |
| 3 | `create_products_table` | `products` |
| 4 | `create_inventory_table` | `inventory` |
| 5 | `create_document_number_sequences_table` | `document_number_sequences` |
| 6 | `create_receiving_documents_table` | `receiving_documents` |
| 7 | `create_receiving_items_table` | `receiving_items` |
| 8 | `create_receipts_table` | `receipts` |
| 9 | `create_inventory_transactions_table` | `inventory_transactions` |
| 10 | `create_idempotency_keys_table` | `idempotency_keys` |
| 11 | `create_append_only_triggers` | `prevent_row_mutation()` function and two triggers |

### 8.3 Running migrations reliably

- The backend container entrypoint waits for the database to be healthy, then runs `php artisan migrate --force`, then starts the web process. `docker compose` uses a PostgreSQL `healthcheck` and `depends_on: condition: service_healthy`.
- Only one backend instance runs migrations. This is guaranteed in this deployment because there is a single `backend` service. If scaled later, run migrations as a separate one-off job.
- Migrations are idempotent in effect: running `migrate` twice does nothing the second time, because Laravel records applied migrations in its `migrations` table.
- A failed migration must leave the database unchanged. PostgreSQL supports transactional DDL, and Laravel wraps each migration in a transaction by default on PostgreSQL. Do not disable this.

### 8.4 Seeding

Seeders must be safe to run repeatedly (`updateOrCreate`, keyed by email or SKU).

| Seeder | Data |
|---|---|
| `UserSeeder` | One Supervisor and one Operator. Email and password come from environment variables with documented demo defaults for local use only (FR-AUTH-6). Never real credentials. |
| `DemoDataSeeder` (optional, local only) | A few products and one sample document, to make the demo quick. Not run in the default production path. |

When a product is created through the application, its `inventory` row is created in the same transaction (FR-PROD-5). Seeders must go through the same service so that rule holds for seeded products.

## 9. Integrity Verification Queries

These queries are used by the tests and in the demonstration evidence (`testing.md`). Each must return zero rows.

```sql
-- 1. Stock on hand equals the sum of the ledger (BR-17)
SELECT i.product_id, i.quantity_on_hand, COALESCE(SUM(t.quantity), 0) AS ledger_sum
FROM inventory i
LEFT JOIN inventory_transactions t ON t.product_id = i.product_id
GROUP BY i.product_id, i.quantity_on_hand
HAVING i.quantity_on_hand <> COALESCE(SUM(t.quantity), 0);

-- 2. Item received quantity equals the sum of its receipts (BR-20)
SELECT ri.id, ri.received_quantity, COALESCE(SUM(r.quantity), 0) AS receipts_sum
FROM receiving_items ri
LEFT JOIN receipts r ON r.receiving_item_id = ri.id
GROUP BY ri.id, ri.received_quantity
HAVING ri.received_quantity <> COALESCE(SUM(r.quantity), 0);

-- 3. No item is over-received (BR-07)
SELECT id FROM receiving_items WHERE received_quantity > expected_quantity;

-- 4. Every receipt has exactly one transaction (BR-13)
SELECT r.id
FROM receipts r
LEFT JOIN inventory_transactions t ON t.receipt_id = r.id
WHERE t.id IS NULL;

-- 5. Running balance of each product is consistent with the ledger
SELECT *
FROM (
    SELECT id, product_id, balance_after,
           SUM(quantity) OVER (PARTITION BY product_id ORDER BY id) AS expected_balance
    FROM inventory_transactions
) x
WHERE balance_after <> expected_balance;

-- 6. No completed document has an unfinished item (BR-08)
SELECT d.id
FROM receiving_documents d
JOIN receiving_items ri ON ri.receiving_document_id = d.id
WHERE d.status = 'COMPLETED' AND ri.received_quantity < ri.expected_quantity;
```

## 10. Design Decisions and Trade-offs

| Decision | Alternative | Why this choice |
|---|---|---|
| Keep `inventory.quantity_on_hand` plus a ledger | Compute stock as `SUM(transactions)` on every read | Fast reads and a simple lock target for concurrency. The cost is two places to keep consistent, which is handled by one transaction and verified by Query 1. |
| Lock the document row first | Lock only the item row | Also serializes against confirm, complete, and cancel. The cost is that receipts on the same document run one at a time, which is acceptable for a warehouse dock. |
| `CHECK` constraints in addition to service validation | Validate only in the application | Protects against bugs and manual database changes. The cost is extra raw SQL in migrations. |
| Denormalized `product_id`, `receiving_document_id`, `receiving_item_id` in `inventory_transactions` | Join through `receipts` and `receiving_items` | History filters stay fast on a large append-only table. The values are written once and can never change (append-only trigger). |
| `VARCHAR` plus `CHECK` instead of native `ENUM` | PostgreSQL `ENUM` | Adding a status later is a simple constraint change, not an enum type alteration. |
| Idempotency results stored in a table | Cache (Redis) | No extra infrastructure, and it commits atomically with the receipt. |
| Daily sequence table for document numbers | Database sequence or `MAX()+1` | A normal sequence cannot reset per day. `MAX()+1` races under concurrency. The upsert is atomic. |
| No `ON DELETE CASCADE` | Cascade from documents to items | Nothing but draft items is ever deleted. Cascading could silently erase history if something went wrong. |

## 11. Known Limitations

- `idempotency_keys` grows without bound. A cleanup job removing keys older than a retention period (for example 7 days) can be added later. Once a key is purged, the same key could be accepted again.
- The ledger supports only `RECEIVE` today. Adding outbound or adjustment types requires changing the `type` check, allowing negative `quantity` (with a sign or direction column), and revisiting `balance_after >= quantity`.
- There is no location, batch, or unit dimension (out of scope, Section 4.2 of the PRD).
- Receipts on the same document are serialized by the document lock. This is a deliberate simplicity trade-off.
